# 앱이 쓰는 부품(의존성) 대장

> **CI 가 지키는 것은 딱 하나 — 표에 이름이 있는가.**
> `app/pubspec.yaml` 에 부품을 넣거나 뺐으면 아래 표에도 한 줄 적어야 통과한다
> (`scripts/harness/check_dependencies.py`).
>
> **`네이티브` 열은 사람이 적는 값이고 CI 는 검증하지 않는다.** 검증하는 척하면
> "막고 있다"는 착각만 남는다. 판정이 헷갈리면 아래 도구를 쓰되, **최종 판단은 사람이 한다.**
> ```bash
> python3 scripts/harness/check_dependencies.py --classify
> ```

## 왜 적나

부품에는 두 종류가 있다.

| 종류 | 무엇 | 위험 |
|---|---|---|
| **순수 Dart** | 앱 코드로만 되어 있다. 어느 폰에서든 똑같이 동작 | 낮음 |
| **네이티브** | 아이폰은 애플 코드, 안드로이드는 구글 코드를 각각 따로 쓴다 | **폰마다 다르게 동작한다** |

네이티브 부품은 **"안드로이드에서 잘 되네"가 증거가 되지 않는다.** 2026-08-04 실제 사례: 웹페이지의 카메라 요청을 안드로이드는 기본 거부하는데 iOS 는 기본이 "사용자에게 묻기"였다. 마이크는 설명이 없으면 앱이 그냥 꺼진다. 안드로이드로 아무리 눌러봐도 이건 안 나타난다.

앱은 이미 스토어에 올라가 있다. 새 부품은 **다음 업데이트를 받는 기존 사용자 전원**에게 나간다.

## ⚠️ "순수 Dart" 가 안전하다는 뜻은 아니다

**직접 부품이 순수 Dart 여도 네이티브 부품을 데려올 수 있다.** 이걸 전이(transitive) 의존성이라 한다.

실제로 이 앱은 직접 부품 17개를 쓰는데 **최종적으로 설치되는 패키지는 182개**다. 분류 도구가 네이티브로 잡는 것이 **49개**인데, 여기엔 `app_links_web` 처럼 웹 전용이나 Linux·Windows 전용도 섞여 있다 — **후보 목록이지 확정이 아니다**.

가장 헷갈리는 예:

| 직접 부품 | 그 자체는 | 그런데 데려오는 것 |
|---|---|---|
| `supabase_flutter` | 순수 Dart | **`app_links`** (iOS·Android 네이티브 — 딥링크 처리), `package_info_plus` |
| `cupertino_http` | 네이티브(FFI) | `objective_c` (FFI 바인딩) |

그래서 아래 표의 `네이티브` 열은 **그 부품 자체**를 가리키고, 마지막 열의 `iOS 확인`은 **데려오는 것까지 포함한 실제 확인 여부**다.

### `미기록` 과 `미확인` 의 차이

- **미기록** — 오래 쓰인 부품이라 실사용으로 검증된 셈이지만, 확인했다는 기록이 남아 있지 않다. 소급해서 채우지 않는다.
- **❌ 미확인** — **새로 들어왔고 아직 아이폰에서 한 번도 확인되지 않았다.** 다음 스토어 빌드 전에 봐야 한다.

## 새 부품을 넣을 때

1. **정말 필요한지 먼저 본다.** 몇 줄로 되는 일에 부품을 넣지 않는다.
2. **네이티브인지 확인한다.** `--classify` 로 출발점을 얻되, 그 부품이 무엇을 데려오는지도 본다.
3. **위 표에 한 줄 적는다.** 안 적으면 CI 가 막는다.
4. 네이티브면 **PR 본문에 "아이폰 확인 필요"를 적고**, 확인한 뒤 마지막 열을 갱신한다.

## 검사 범위

`app/pubspec.yaml` 의 **`dependencies` 와 `dev_dependencies` 둘 다** 본다. `sdk: flutter` 로 딸려오는 것(`flutter` `flutter_test` `integration_test` 등)만 제외한다.

> **"dev 는 앱에 안 들어간다"는 전제는 사실이 아니다.** 실제로 `integration_test`(dev)가 `app/ios/Runner/GeneratedPluginRegistrant.m` 에 **iOS 네이티브 플러그인으로 등록**돼 있다(2026-08-04 실측). dev 쪽에 플러그인을 넣어 대장을 우회할 수 있어 같이 본다.

## 이 검사가 못 막는 것

정직하게 적어 둔다 — 믿고 방심하지 않도록. **CI 는 이름만 본다.**

- **기존 부품의 버전만 올려** 새 네이티브 전이 의존성이 딸려오는 경우
- 대장에 `네이티브: 아니오` 라고 **틀리게 적는 경우**
- 기존 부품의 **출처만 바꾸는 경우** — `intl: ^0.20.0` 을 `intl: {git: ...}` 로 바꾸면 이름이 같아 그대로 통과한다. 네이티브 코드가 든 다른 구현으로 바뀔 수 있다
- 대장 표의 **설명을 성의 없이 적는 것** (이름만 있으면 통과)

반대로 **CI 가 실패시키는 것** (실측 확인함):

| 시도 | 결과 |
|---|---|
| 대장에 안 적고 부품 추가 | ❌ 실패 |
| 부품 뺐는데 대장에 남김 | ❌ 실패 |
| 따옴표 키 `"camera": ^0.1` | ❌ 실패 (못 읽는 형식) |
| 명시적 키 `? camera` / `: ^0.1` | ❌ 실패 |
| `dependency_overrides` (따옴표 포함) | ❌ 실패 |
| `pubspec_overrides.yaml` 추가 | ❌ 실패 |
| 문서 아무 데나 표 한 줄 넣기 | ❌ 실패 (구분자 밖은 안 읽음) |
| 콜론 있는 주석 `# source: pub.dev` | ✅ 통과 (오탐 아님) |
| git·path 의존성 선언 | ✅ 통과 |
