# 챗봇 확장 — 대회 검색 / 일정 겹침 확인 / 랭킹 조회 (설계)

> 작성일: 2026-08-18
> 상태: 설계 승인됨 (Commander), 구현 계획 전 단계
> 관련 리서치: `docs/research/sports-app-retention-feature-benchmark.md`
> 관련 전략: `docs/superpowers/specs/2026-05-29-strategy-and-roadmap-design.md` (Post-MVP 백로그 1순위: A2UI/챗봇 확장)

## 1. 배경

대회 참가 신청/결제 기능은 협회 계약·PG 연동이 필요해 의도적으로 보류 중이다
(관련 메모: `tournament-entry-payment-bm-backlog`). 신청 기능 없이도 재방문(리텐션)을
만들 방법을 브레인스토밍한 결과, Match-up이 경쟁작 대비 유일하게 가진 자산인
AI 챗봇을 "질문에 텍스트로 답만 하는" 수준에서 "구조화된 조회를 대신 해주는" 수준으로
확장하는 방향으로 스코프가 좁혀졌다.

리서치(`sports-app-retention-feature-benchmark.md`)에서는 "챌린지 래더"(도전-셀프리포트-
즉시순위갱신)가 가장 강한 리텐션 신호로 확인됐으나, 이번 스코프는 그 전 단계로
**이미 있는 데이터(대회, 일정, 랭킹)를 챗봇으로 더 쉽게 꺼내 쓰게 만드는 것**에 집중한다.

## 2. 목표

챗봇이 다음 세 가지 조회를 직접 수행하고 자연어로 답하게 한다:

1. **대회 검색/추천** — 사용자 등급/지역에 맞는 대회를 챗봇 대화로 찾음 (기존 `tournaments-search`를 챗봇 경로에서도 쓸 수 있게)
2. **일정 겹침 확인** — 즐겨찾기한 대회와 클럽 모임 일정 중 날짜가 겹치는 것을 찾아 알려줌
3. **랭킹 조회** — 본인 인증 연결(`org_player_links.status='confirmed'`)이 된 사용자에 한해 랭킹 포인트/순위를 알려줌

## 3. 범위

### 포함

- 위 세 가지 **조회(읽기)** 기능의 챗봇 통합
- 의도 분류(사용자 메시지가 셋 중 무엇에 해당하는지 판단) + 폴백(기존 일반 챗봇 흐름)
- 정확성이 필요한 계산(날짜 겹침 판정, 포인트 조회)은 코드가 하고 AI는 결과를 문장으로 바꾸는 역할만

### 제외 (다음 스코프)

- **쓰기 작업** — 챗봇이 즐겨찾기 추가, 알림 설정 등을 대신 실행하는 것. 지금 챗봇 UI가 텍스트 전용(버튼/카드 없음, A2UI는 Phase 2 미착수)이라 텍스트만으로 쓰기 확인을 받는 건 오해 리스크가 있어 이번엔 제외.
- **본인 인증 연결 플로우 신규 구축** — 랭킹 조회는 "이미 연결된 사람만" 대상으로 하고, 연결 자체를 만드는 기능(신원 확인 로직 포함)은 별도 스코프로 분리. 현재 `confirmed` 연결이 0건에 가까워 대부분 사용자는 "연결 안 됨" 응답을 받게 됨 — 이는 알려진 제약이며 이번 스코프의 목적이 아니다.
- **클럽 관련 쓰기 작업** (가입 신청, 모임 생성 등) — 챗봇이 클럽 데이터를 다루는 건 일정 겹침 확인을 위한 **조회**(`club_events` 날짜 읽기)로 한정. 클럽 가입/모임 관리 자체를 챗봇 액션으로 만드는 건 범위 밖.

## 4. 아키텍처

```
사용자 메시지
   ↓
① 의도 분류 (규칙 매칭 우선, 애매하면 저비용 LLM 1회 호출)
   ↓
   ├─ 대회검색 / 일정겹침 / 랭킹조회 중 하나로 판단됨
   │     ↓
   │   ② 결정론적 코드가 DB에서 정확한 결과를 구함 (AI는 계산하지 않음)
   │     ↓
   │   ③ 그 결과(JSON)를 Gemini에게 주고 "이 데이터만으로 자연스러운 문장을 만들어라,
   │       새로운 사실을 추가하지 마라"는 지시와 함께 답변 생성 → 기존 SSE 스트림으로 전송
   │
   └─ 셋 다 아님 (일반 질문)
         ↓
       기존 RAG + Search Grounding 흐름 그대로 (변경 없음)
```

**핵심 원칙**: 겹침 여부·포인트 같은 정답이 있는 값은 항상 서버 코드가 계산하고 AI는
그 결과를 말로 풀어주는 역할만 한다. AI가 날짜를 직접 비교하거나 점수를 추정하지 않는다
(서버/DB가 자격·판단의 근거라는 프로젝트 원칙, `CLAUDE.md` 규칙 2와 일치).

**확인 필요 (구현 계획 단계)**: 이 설계는 `docs/rules/PROJECT_CONTEXT.md`에 문서화된
`/chat` 엔드포인트 구조(SSE, RAG + Search Grounding)를 기준으로 추정했다. 이번 브레인스토밍
세션에서는 `supabase/functions/chat/` 실제 코드를 파일 권한 문제로 읽지 못했으므로,
Gemini function calling과 기존 Search Grounding을 같은 요청에서 동시에 못 쓰는 API 제약이
있는지, 기존 코드가 의도 분류 단계를 끼워 넣기 쉬운 구조인지는 구현 계획을 쓰기 전에
반드시 실제 코드로 재확인한다.

## 5. 컴포넌트

- **의도 분류기**: 키워드 매칭 우선 ("대회/찾아줘/검색" → 대회검색, "겹치/일정/스케줄" →
  일정겹침, "랭킹/포인트/등수" → 랭킹조회). 매칭이 애매하면 저비용 LLM 호출 1회로 4개
  라벨(대회검색/일정겹침/랭킹조회/일반질문) 중 하나만 고르게 한다.
- **조회 처리기 3개**: 대회검색은 기존 `tournaments-search` 로직을 재사용(가능하면 공유
  모듈로 추출, 어렵다면 구현 단계에서 구조 재검토). 일정겹침·랭킹조회는 신규 순수 조회 함수.
- **응답 포맷터**: 조회 결과를 JSON으로 정리해 Gemini에게 넘기고 "이 데이터만으로 답하라"고
  명시한다.

## 6. 데이터

| 조회 | 사용 테이블 |
|---|---|
| 대회검색 | 기존 `tournaments-search`와 동일 (`tournaments` 등) |
| 일정겹침 | `tournament_favorites`, `tournaments`(날짜), `club_events`(날짜) — 로그인 사용자 기준 |
| 랭킹조회 | `org_player_links`(status='confirmed') → `org_player_results` / `org_rankings` |

## 7. 에러 처리

- 랭킹조회인데 `confirmed` 연결이 없음 → AI 호출 없이 고정 안내문으로 즉시 응답 (비용 절감 + 오답 방지)
- 일정겹침인데 비교할 즐겨찾기/모임이 없음 → 고정 안내문
- 의도가 애매하거나 셋 다 아님 → 기존 일반 챗봇 흐름으로 폴백 (안전한 기본값, 기존 기능 비파괴)
- DB 쿼리 실패 → 기존 챗봇 에러 처리 방식을 따른다 (구현 단계에서 실제 코드 확인)

## 8. 테스트

- **일정겹침 판정**: 순수 날짜 비교 로직이므로 겹침/안겹침 케이스로 자동 테스트 작성
- **랭킹조회**: 연결됨/안됨 두 케이스
- **의도 분류**: 대표 문장 세트로 분류 정확도 확인
- **회귀**: 폴백 경로(기존 일반 챗봇 흐름)가 이번 변경으로 깨지지 않는지 확인

## 9. 열린 질문 / 리스크

- Gemini function calling과 기존 Search Grounding 동시 사용 가능 여부 — 구현 전 확인 필요
- `tournaments-search` 로직을 챗봇 경로와 공유하는 구체적 방법(공유 모듈 추출 vs 내부 호출) — 구현 단계에서 실제 코드 구조 보고 결정
- 저비용 LLM 의도 분류 호출이 챗봇 응답 지연(latency)에 얼마나 영향을 주는지 — 구현 후 실측 필요
