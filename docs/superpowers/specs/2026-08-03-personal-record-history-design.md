# 개인 기록장 (내 순위 변화 · 라이프베스트) — 설계

- 작성일: 2026-08-03
- 선행: `2026-08-03-org-ranking-mirror-design.md` (협회 랭킹 미러링)
- 상태: Commander 승인 완료, 구현 계획 대기

---

## 1. 목적

사용자가 **자기 기록이 쌓이는 걸 보려고 앱을 다시 여는 것.** 리텐션이 목적이고, 기록 자체가 제품이다.

Commander 표현: "내 기록장이 되어야지 이 앱을 계속 사용하지 않을까". 참조는 골프존 앱 — 라이프베스트, 최고 상승, 세세한 이력.

**골프존과 결정적으로 다른 조건**: 골프존은 스크린에서 친 순간 자동 기록되고, 점수를 매기는 주체가 골프존 자신이다. 우리는 (1) 자동 기록 장치가 없고 (2) 점수는 협회가 매긴다. 이 두 제약이 아래 결정을 지배한다.

## 2. 현재 상태 (2026-08-03 실측)

| 것 | 상태 |
|---|---|
| `org_rankings` | **3,540행** (2개 협회 · 12개 부서). 크롤러 가동 중 |
| `org_player_links` (본인 연결) | **0건** (승인 0) |
| `match_entries` / `match_rounds` | 테이블·API 모두 있으나 **0행**, 화면에서 아무도 호출 안 함 |
| 프로필 "내 대회 기록" 섹션 | **이름만 기록.** 실제로는 즐겨찾기 대회 목록(`myFavoriteTournaments`) |
| 앱 사용자 | 19명 |

**핵심**: `org_rankings` 는 현재 스냅샷만 보관하고 `replace_org_ranking_division` 이 부서 단위로 통째 교체한다. 시간 축이 없어 "내 순위 변화"를 만들 수 없다.

## 3. 확정된 결정

| # | 결정 | 근거 |
|---|---|---|
| 1 | 기록의 원천은 **협회 랭킹**. 소모임·기타 이력은 범위 밖 | Commander |
| 2 | 연결 승인자의 **개인 대회 이력 페이지를 크롤한다** (`sub4_6_rank.php?userid=`) | Commander — 협회 동의 범위 안 |
| 3 | **앱이 자체 점수·레벨을 만들지 않는다.** 협회 숫자에서 파생된 사실만 보여준다 | Commander — 선행 설계 §5 공식 오인 리스크와 일관 |
| 4 | 순위 스냅샷은 **전원 저장** (연결자 한정 아님) | Commander — 나중에 연결한 사람도 과거를 갖게 하려고 |
| 5 | 구현은 **개인 이력 먼저 → 순위 그래프 나중** | Commander — 그래프는 스냅샷이 쌓인 뒤 켠다 |

### 결정 4에 대한 주석

선행 설계 §4.2 는 스냅샷 이력을 포기하며 이유를 "크롤마다 수천 행 **실명** 누적"이라고 적었다. **이 설계의 스냅샷 테이블에는 실명이 없다** — `org_player_id` 만 담는다. 그래서 그 우려가 그대로 적용되지 않는다.

부피는 하루 3,540행 · 연 약 130만 행. Postgres 기준 부담되는 크기가 아니다.

## 4. 두 원천이 서로 다른 것을 준다

이 구분이 설계의 뼈대다.

| 원천 | 주는 것 | 시간 범위 |
|---|---|---|
| 개인 이력 페이지 | 대회별 성적 · 획득 포인트 · 대회일 → **라이프베스트, 최고의 순간, 전적 타임라인** | **과거 포함** (실측: 김평화 46건, 2025-12까지) |
| 순위표 스냅샷 | 부서 내 순위 · 누적 포인트의 시간 축 → **순위 변화 그래프** | 지금부터 |

개인 이력 페이지의 `순위` 컬럼은 **그 대회에서의 성적**(우승·4강)이지 부서 내 랭킹 순위가 아니다. 따라서 "내 순위 변화"에는 스냅샷이 반드시 따로 필요하다.

## 5. 데이터 모델

### 5.1 `org_player_results` — 개인 대회 이력

```
id              uuid pk default uuid_generate_v7()
org_code        text not null
org_player_id   text not null
tournament_name text not null
played_on       date not null
event_raw       text            -- 종목(출전 부서) 원문
result_raw      text not null   -- 순위 표기 원문
result_round     int             -- 정규화값 (1=우승, 2=준우승, 4=4강…), 못 읽으면 NULL
points          int not null default 0
fetched_at      timestamptz not null default now()

unique (org_code, org_player_id, tournament_name, played_on)
```

**`result_raw` 원문 보존이 필수다.** 협회 표기가 `1`·`4`·`8`·`16` 과 `16강`·`4강`·`32강` 으로 한 컬럼에 섞여 있다(선행 설계 §2.2 실측). 파싱이 실패하면 `result_round` 를 NULL 로 두고 원문을 남긴다 — **추측값이나 0으로 채우지 않는다.** 표기가 더 발견되면 원문에서 소급 정규화한다.

`event_raw ≠ 랭킹 부서`다. 골드부 랭킹인 선수가 지동부·남자오픈부로도 출전해 포인트를 얻는다. 화면에서 이 둘을 섞지 않는다.

### 5.2 `org_ranking_snapshots` — 순위 추이

```
id            uuid pk default uuid_generate_v7()
org_code      text not null
division_code text not null
org_player_id text not null
captured_on   date not null
rank          int not null
total_points  int not null

unique (org_code, division_code, org_player_id, captured_on)
```

하루 1행. **실명 없음** — 표시할 때 `org_rankings` 의 현재 명단과 조인한다.

### 5.3 RLS

두 테이블 모두 RLS 필수(`CLAUDE.md` 최소 규칙 3). 정책은 **본인 것만 읽기**:

- 조건: `org_player_id` 가 **내 승인된 `org_player_links`** 와 일치
- 쓰기는 `service_role` 전용 (크롤러 경로)
- **정책에 `TO authenticated` 를 명시한다** — 생략하면 PUBLIC 이 되어 anon 조회가 42501 로 죽는다(#365 에서 33개 테이블이 이 함정에 걸려 있었다)

새 함수를 만들면 `grant execute ... to authenticated` / `to service_role` 을 같은 마이그레이션에 명시하고, 회수할 때는 `from public, anon, authenticated` 셋 다 떼고 필요한 롤에 다시 부여한다(#379).

## 6. 수집 흐름

### 6.1 순위 스냅샷 — 크롤링이 아니라 DB 내 복사

**실행 위치**: 기존 `replace_org_ranking_division` RPC **안에서** 교체와 같은 트랜잭션으로 적재한다. 새 호출 지점도, 새 cron 도 만들지 않는다.

이유는 셋이다.

1. **부서 단위로 신선하다.** 부서 교체 직후에 그 부서만 찍으므로 모든 스냅샷 행이 방금 크롤한 값이다. 사이클 끝에 한 번 찍으면 부서마다 교체 시각이 달라(순차 실행) 한 `captured_on` 안에 옛 부서와 새 부서가 섞인다.
2. **실패한 부서는 그날 점이 안 생긴다.** 0행 가드에 걸려 교체를 건너뛴 부서는 RPC 자체가 호출되지 않으므로 낡은 값이 오늘 날짜로 박히지 않는다. 그래프에 구멍이 남는 편이 거짓 점보다 정직하다.
3. **원자적이다.** 교체가 롤백되면 스냅샷도 롤백된다. 별도 호출이면 교체 성공 + 스냅샷 실패가 조용히 갈린다.

새 HTTP 요청 0건.

```sql
-- replace_org_ranking_division 끝, 새 행을 넣은 직후
insert into org_ranking_snapshots (org_code, division_code, org_player_id, captured_on, rank, total_points)
select r.org_code, r.division_code, r.org_player_id, current_date, r.rank, r.total_points
  from org_rankings r
 where r.org_code = p_org and r.division_code = p_division
   and r.org_player_id is not null
on conflict do nothing;
```

`on conflict do nothing` 이라 같은 날 크롤이 여러 번 돌아도 행이 늘지 않는다. **그날 첫 크롤 값이 남는다** — 나중 값으로 덮지 않는다. 하루 한 점이면 충분하고, 덮어쓰기를 넣으면 "언제 찍은 값인가"가 흐려진다.

### 6.2 개인 이력 — 실제 크롤 (연결 승인자만)

- 대상: `org_player_links.status = 'confirmed'` 인 사람의 `org_player_id`
- URL: `{base}/sub4_6_rank.php?userid={org_player_id}`
- 요청 수 = **승인자 수** (선행 설계가 이 크롤을 미룬 이유는 "선수당 1요청 × 수천 명"이었다. 연결자 한정이면 그 이유가 사라진다.)
- 시점: **연결 승인 직후 1회** + 이후 랭킹 크롤 사이클에 묻어서 갱신
- 파서는 `_shared/crawler/parsers/gnuboard_ranking.ts` 옆에 별도 파일로 둔다

대회는 매일 열리지 않고 협회 반영도 폐막 후 3일 이내다. 자주 긁을 이유가 없다.

## 7. 화면

**진입점**: 프로필(MY)의 "내 대회 기록" 섹션을 **진짜 기록으로 교체**한다. 지금 그 자리는 이름과 내용이 어긋나 있다(즐겨찾기 목록 + 실패 시 목업).

### 7.1 미연결 사용자 (현재 전원)

연결 유도 카드. `my_ranking_candidates()` 가 이름·소속 협회·등록 부서로 후보를 뽑아주므로 **후보 제시 → 원탭 신청 → 관리자 승인** 흐름을 그대로 쓴다.

**여기가 막히면 기능 전체가 죽는다.** 승인 0건인 현재 상태에서 가장 공들일 자리다.

### 7.2 연결자 화면 — 위에서부터

| # | 블록 | 내용 | 원천 | 단계 |
|---|---|---|---|---|
| 1 | **지금** | 부서 · 순위 · 누적 포인트 | `org_rankings` (현재값) | 1 |
| 2 | **라이프베스트** | 최고 순위(달성일), 최고 누적 포인트 | 스냅샷 | 2 |
| 3 | **최고의 순간** | 단일 대회 최다 획득 (`광주시장배 우승 +1000`) | 개인 이력 | **1** |
| 4 | **순위 추이** | 꺾은선 + 최근 변화 (`▲5계단`) | 스냅샷 | 2 |
| 5 | **전적** | 대회별 타임라인 (대회명 · 성적 · 포인트 · 종목 · 날짜) | 개인 이력 | **1** |

**순위에 관한 것은 전부 2단계다** — 라이프베스트의 "최고 순위"와 "최근 변화" 모두 스냅샷이 필요하다. 1단계에서는 이 블록들을 아예 그리지 않는다. 빈 그래프나 "데이터 없음"을 띄우지 않는다.

1단계만으로도 **최고의 순간 + 전적 타임라인**이 과거 데이터로 채워져 화면이 성립한다. 그것이 개인 이력을 먼저 하는 이유다.

### 7.3 표기 규칙

- **출처와 갱신 시각을 매 화면에 표시**한다. "협회 공표 기준".
- 우리가 매긴 점수가 아님이 계속 보여야 한다 (결정 3).
- `result_round` 가 NULL 인 행은 `result_raw` 원문을 그대로 보여준다. 빈칸이나 추측값으로 대체하지 않는다.

### 7.4 시즌 경계

2027년 1월 협회 포인트 리셋(선행 설계 §7). 누적 포인트·순위는 초기화되지만 **개인 이력은 `played_on` 이 있어 남는다.** 리셋 후에도 "2026 시즌 라이프베스트"가 유지된다 — 이 설계가 리셋에 강한 이유다.

라이프베스트는 시즌 구분해 표시한다.

## 9. 테스트

| 대상 | 방법 |
|---|---|
| 개인 이력 파서 | Deno 테스트. **순위 표기 혼재**(`1`/`16강`) 고정 픽스처로 정규화·NULL 처리 검증 |
| RLS | pgTAP. 남의 `org_player_id` 행이 안 보이는지, anon 조회가 **에러가 아니라 0행**인지(#365) |
| 함수 권한 | 기존 `021_function_execute_grants` 가 자동으로 잡는다 (트리거 함수 규칙 + anon 허용 목록 대조) |
| 스냅샷 멱등성 | 같은 날 두 번 실행해도 행이 늘지 않는지 |

**변이 주입으로 역검증한다.** 초록불은 증거가 아니다 — 각 단언에 위반 데이터를 넣어 실제로 뒤집히는지 확인한 뒤에만 통과로 친다.

## 10. 미해결

1. **연결 승인이 수동이다.** 관리자가 한 건씩 승인한다. 사용자가 늘면 병목이 된다. 자동 승인 조건(이름 + 협회 + 부서 + 클럽 완전 일치 등)은 별건으로 판단한다.
2. **`org_player_id` 안정성.** 협회가 아이디를 바꾸면 이력이 끊긴다. 실측된 적 없음.
3. **개인 이력 페이지의 대회명이 우리 `tournaments` 와 매칭되는지** 확인 안 됨. 매칭되면 대회 상세 연결이 열리지만 지금은 근거가 없어 범위 밖.
4. **스냅샷 시작일 이전 구간**은 그래프에 없다. 개인 이력의 대회일·포인트로 순위를 역산할 수 있는지는 검토 안 함(협회가 0점 선수를 명단에 포함하므로 역산은 부정확할 가능성이 높다).
